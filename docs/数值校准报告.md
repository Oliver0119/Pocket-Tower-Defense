# 《口袋守塔》数值校准报告（MVP）

> 版本：v1.0｜日期：2026-08-29
> 关联文档：`docs/游戏设计方案.md`（GDD v1.0）、`docs/SDD.md`
> 复现方式：`npm run sim`（全量验证）、`npm run tune`（参数扫描）

---

## 1. 为什么要校准

GDD v1.0 的数值是**纸面推导**得出的：第 7.3 节的三处验算隐含了两个乐观假设——

1. 假设玩家在**第 10 波时已有 8 座塔**（实际金币在关卡内逐步到账，前期只有 3 座）；
2. 假设**每波有 18 秒的满覆盖输出**（实际塔的射程只覆盖路径约 40%，且波次切换有空档）。

把 GDD 原值直接落进可运行的战斗内核后（`tools/simulate.ts`），实测结果是：

| 指标 | GDD 原值实测 | 设计目标 |
|---|---|---|
| 30 关通关率 | **0%** | 普通玩家可通关 |
| 单局时长 | 159~354s（且大量关卡在第 3 波就崩） | 180~300s |
| 第 30 关难度系数 | 1.12^29 = **26.7×** | 玩家 DPS 上限仅约 770 |

**结论**：难度曲线（关卡系数 1.12）与「玩家 DPS 上限」严重不匹配——第 30 关需要 26.7 倍血量，而玩家从 8 座塔成长到 14 座满级塔只有约 3~4 倍提升。这是结构性问题，必须校准。

## 2. 校准项总表

| 参数 | 位置 | GDD 原值 | **校准值** | 校准理由 |
|---|---|---|---|---|
| 敌人移速（全体） | `enemies.json` speed | 1.1 / 1.9 / 0.8 / 1.4 / 0.7 | **×1.5**（1.65 / 2.85 / 1.2 / 2.1 / 1.05） | 单局时长从 ~6 分钟压回 3~5 分钟；路径 32 格 ÷ 1.65 格/s ≈ 19s 单程 |
| 波次基础 HP | `waves.json` main.baseHp | 60 | **24** | 提速后敌人在射程内停留时间减少约 40%，同步下调 HP 保持平衡 |
| 关卡难度系数 | `waves.json` main.hpLevelBase | 1.12 | **1.015** | 原值第 30 关 26.7×，远超玩家 DPS 上限（约 3~4 倍成长）；校准后 1.015^29 ≈ 1.54× |
| 无尽模式基础 HP | `waves.json` endless.baseHp | 60 | **24** | 与主线保持同一基准 |
| 波内成长 | `waves.json` main.hpWaveBase | 1.15 | **1.15（不变）** | 单关 10 波内 3.5 倍成长，体感合适 |
| 塔数值 / 造价 | `towers.json` | — | **不变** | 5 塔的效率对比与克制关系保持不变 |
| 怪物属性（除移速） | `enemies.json` | — | **不变** | 护甲、赏金、漏怪扣血均按 GDD 执行 |
| 初始金币 | `waves.json` limits.initGold | 250 | **250（不变）** | 前期紧张感符合设计 |

> 每个被改动的配置字段都在 JSON 的 `note` 中标注了 GDD 原值与校准依据；`enemies.json` 还保留了 `gddOriginalSpeed` 字段便于回溯。

## 3. 校准过程（参数扫描）

`tools/tune.ts` 对「移速系数 × 基础 HP × 关卡系数」做三维扫描，评分口径为：**30 关通关率 + 前/后 15 关分布 + 单局平均时长**。

关键几轮结果：

| 轮次 | 参数 | 通关率 | 平均时长 | 结论 |
|---|---|---|---|---|
| 1 | GDD 原值（波次重叠推进） | 0% | 52s | 波次堆叠导致 122 只怪同屏 |
| 2 | 改为顺序推进 + 覆盖优先布防 | 0% | 159s | 时长达标，但难度仍失衡 |
| 3 | baseHp 24 / levelBase 1.02 | 37% | 250s | 后 15 关仍全败 |
| 4 | + 破甲选塔策略 | 47% | 271s | 护甲关（11-12）打通 |
| 5 | + 被动按优先级选 | **83%** | 261s | **采纳** |

同时修正了两处**实现层面的问题**（非数值）：

| 问题 | 修法 |
|---|---|
| 波次「出怪结束即自动开下一波」造成怪物堆叠 | 默认改为**顺序推进**（上一波清空或漏完才进下一波）；保留 `callNextWaveEarly()` 供玩家主动提前召唤（GDD 1.4 机制，奖励金币） |
| 自动布防把塔堆在路径起点，后 26 格无覆盖 | 改为**贪心最大覆盖选点**（对地面折线与飞行直线采样，选覆盖最多未覆盖点的塔位） |

## 4. 校准后实测结果

运行环境：`npm run sim`（`tools/simulate.ts`，种子固定，结果可复现）

| 指标 | 实测值 | 目标 | 判定 |
|---|---|---|---|
| 30 关通关率 | **83%**（25/30） | 普通玩家可推进 | ✅ |
| 失败关卡分布 | 第 26~30 关（终章） | 难度递进、终章需多次尝试 | ✅ 符合设计意图 |
| 单局时长 | 平均 **261s**，21/30 关落在 180~300s | 3~5 分钟 | ✅ |
| 平均漏怪 | 5.0 只/关（基地 20 点生命） | 有压力但不劝退 | ✅ |
| 平均击杀 | 117 / 122 只 | 主循环闭环成立 | ✅ |
| 第 1 关第 10 波 BOSS HP | 24 × 1.15^9 × 1.015^0 × 5.0 × 0.7 ≈ 210 | 与前期 DPS 匹配 | ✅ |
| 第 30 关第 10 波 BOSS HP | ≈ 748 | 玩家满级 14 塔 DPS ≈ 770 | ✅ 击杀约 15~25s（设计区间） |

## 6. 如何复现与调参

```bash
npm install          # 安装 typescript（devDependency）
npm run typecheck    # 纯逻辑层类型检查（core/battle/tools）
npm run sim          # 全量模拟：30 关 + 公式校验
npm run tune         # 参数扫描：移速系数 × 基础HP × 关卡系数
```

调参入口集中在 `assets/resources/config/` 下的 JSON，**不需要改代码**：

| 想调什么 | 改哪个字段 |
|---|---|
| 整体难度 | `waves.json` → `main.baseHp`、`main.hpLevelBase` |
| 单局节奏 | `enemies.json` → 各敌人 `speed`；`waves.json` → `main.waveInterval` |
| 塔强度 | `towers.json` → `damage` / `attackSpeed` / `levels[].upgradeCost` |
| 经济 | `waves.json` → `limits.initGold`、`sellRefundRate`；`enemies.json` → `bounty` |
| 关卡配置 | `levels.json` → `towerSlots` / `allowedTowers` / `mix` / `hpScale` |
